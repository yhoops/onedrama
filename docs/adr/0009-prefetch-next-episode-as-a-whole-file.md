# 预取下一集用整集落盘，而不是只预取头部

[ADR-0005](0005-client-side-cenc-decryption.md) 花了大力气做**流式解密**，为的是「不用等整集下完就能开播」。现在却反过来：播放时后台把**下一集整集下完并解密落盘**（复用 `lib/data/media_cache.dart` 的 `prepareEpisode`），切集时直接播本地文件。看起来是自相矛盾，所以写清楚。

两者解决的不是同一件事：

| | 流式解密（ADR-0005） | 预取（本条） |
| --- | --- | --- |
| 解决 | 一集**开始播**要等整集下完（15 MB） | **切下一集**要等 2.3 秒 |
| 实测 | `STATE_READY` 458–613 ms（本地文件）→ 2257 ms（流式） | 同上，切集落回 458–613 ms |
| 代价 | 无额外磁盘 | 每集 14.6 MB 临时文件 |

真正让「整集落盘」胜出的是另一个不显然的理由：**`media.url` 带时效签名**（`lib/data/network.dart` 特意说明取流一律不缓存就是这个原因）。所以「只预取头部 + 解密计划」这条路预存的是**一个会过期的 URL**——用户暂停二十分钟再切下一集，预取的 URL 可能已经失效，还得回头重签一次。文件一落盘就与签名无关了。

## Considered Options

- **只预取取流结果 + 1 MB 头部 + 解密计划**（约 1 MB/集）：几乎不占带宽与磁盘，切集从 2.3 秒降到 1 秒多；代价是上面那条 URL 过期问题，收益也小一截。
- **预建第二个播放器把下一集缓冲好**，切换只换纹理：三者里最快。`MainActivity` 已经是按 `textureId` 管多个实例的，支持得了；但 Dart 侧要同时管两个播放器、两个纹理与各自的释放，复杂度明显上升，也最易出错。

## Consequences

- `_prepare` 的主路径要改：从「能算出解密计划就走流式」变成「**本地有 `cenc_<vid>.mp4` 就播文件，没有才流式**」。预取到的集瞬时，没预取到的集仍是 2.3 秒。
- 落盘的文件在 `getTemporaryDirectory()`（Android 的 cacheDir），**只留最近 10 集**（约 146 MB），更早的按文件时间删。不指望系统回收兜底。
- 预取会与当前集**抢带宽**：一集两分钟、14.6 MB，等于把下行占用翻倍。弱网下当前集可能因此卡顿——这是这条路的主要代价，接受它。
- 当前集开始播放后**立刻**开始预取。**曾经排的是「开播后等 10 秒」**（初衷是别为点进去看一眼就退的人白下 14.6 MB），真机反馈否掉了它：实测一集 10.9–18.8 MB 只要 3–4 秒下完，而人往往看十来秒就往下切——等 10 秒才开始等于 13–14 秒才就绪，切集时照样等加载。改成即开始，白下的代价按取舍接受。
- 不限网络，但设置「播放」组给一个**预缓存下一集**开关，与「自动播放下一集」解耦——关掉连播仍然预取，因为你可能手动点下一集。退出播放页取消预取。
- 预取进行中用户切集：这一集走流式，预取**继续跑完**（下次切回来就快）。解密失败不落坏文件（`.part` → rename 保证了这点）。
