# 剧库部数与「本次新增」只算分类标签，综合不计

设置页「更新剧库」那一行要显示「267 部 · 3 分钟前」，跑完还要弹一句「本次新增 12 部」。这两个数都**只算真人剧 / 漫剧 / AI剧 三个分类标签**，综合不计——尽管综合的 90 部同样躺在 `library_entries` 里。

理由是一次实测：**综合走推荐接口，连拉两次第 1 页只有约六成重叠**（18 部里 11 部相同、7 部是新面孔）；而分类接口按 `online_time` 排序，两次 18 部**完全一致**。把综合算进去，「新增」会常年顶在几十部，而上游一部都没上——那个数字就不值得看了。分类接口的确定性还带来一个好处：「新增」正好等于「上游新上架的」，因为新剧会挤进头部。

代价是设置页显示的部数**小于快照行数**（四个标签约 345 行，部数约 255）——同一部剧会同时出现在综合与漫剧里，按行数算会重复计，所以部数用的是 `COUNT(DISTINCT drama_id)`。行数用户看不到，这个不一致不外显。

## Considered Options

- **四个标签全算，按 ID 去重**：口径最统一（就是「快照全量 diff」），实现也最简。但推荐流的噪声会把真实上新淹掉。
- **四个标签全算，按快照行数**：一条 `COUNT(*)` 就够，但同一部剧在综合和漫剧里各算一次，与「剧库里有多少部剧」的直觉不符。
- **把综合移出导入范围**（只导三个分类标签）：口径最干净——「剧库」就只指确定性的分类内容。但断网时首页的综合标签会变成空白，而现在是能显示上次推荐的一屏的。本地优先这条不划算。

## Consequences

- **「新增」是头部口径**：导入只拉每个标签 5 页（90 部），新剧挤进窗口、老的掉出去。所以部数会在 255–270 上下浮动、很少大幅变动，而「新增」反映真实上新。
- **首次导入不报「新增」**：全新安装与清缓存之后旧快照是空的，那时「新增」就是全部部数，报出来像是上游一次上了 270 部。设置页在这时只更新那一行的数字，不弹窗（见 `LibraryImportReport.firstImport`）。
- **新增要在替换前读旧快照**：`replaceLibraryTab` 是先 delete 再 insert，替换之后就问不出「上次有哪些」了。所以 `LibraryImporter._run` 开头就把分类标签的剧 ID 读出来。
- **「上次更新」那个时间戳也跟着收窄了**：它原来在任一标签成功时就推进（ADR-0008），现在只跟分类标签走。否则综合成功、三个分类标签全挂时，那一行会说「267 部 · 刚刚」——可那个 267 是两天前的。宁可显示「2天前」，那正是最需要知道的时候。
- 词的边界写进了 `CONTEXT.md` 的 **Library Count** / **Newly Added**：前者是「剧库里有多少部剧」，后者是「上游新上、本地还没有的」。
