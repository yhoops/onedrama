# 每次启动把剧库拉一份到本地，首页改成本地优先

首页此前每次都从上游拉：冷启动要等网络才出内容，断网就是整页空。而**同一套兜底已经在榜单上用过**——上游在两种渲染间摇摆时（见 `docs/plan.md`「榜单的上游摇摆」），`RankingCache` 把上一次成功的结果落进 prefs，进榜单页先显示旧榜、再后台刷新。

现在把这条口径推到剧库：**每次启动自动从红果拉四个一级标签各 5 页**（`limit=18`，共 360 部、**20 次签名请求**），写进本地新表；首页（`lib/ui/library_page.dart`）改成**本地优先**——本地有就立刻渲染、**一个请求都不等**，本地为空（首装、或刚按过「清除缓存」）照旧走网络。封面一起落盘（约 8.6 MB），否则断网时首页是一排灰块。

后台那一趟网络**不整页替换**，只做「头部有没有新剧」的检查：把没见过的插到最前，已在列表里的一律不动。原设计写的是「拉到就替换」，但「综合」走的是推荐流、每页都不一样，整页换会让用户眼前的列表自己跳一次。本地为空时这一页才当首屏用。

**每次启动固定多出 20 次签名请求是刻意的**，不是泄漏：换来的是冷启动秒开与断网可刷。这也意味着本地快照是**整批覆盖**的，不累积——累积式会让表涨到几千行，还得为「这次新拉到的排在哪个位置」另定一套规则。

**快照的唯一写入者是「更新剧库」**（自动那一轮 + 设置里手动那一轮）。首页滑到底的翻页只进内存，下拉刷新也只进内存：下拉刷新只拉得回 18 条，落盘会把另外 72 部离线可看的剧删掉。

## Considered Options

- **只做冷启动缓存、不落盘**：改动更小，但断网仍然没用，且在「剧库与存储」这个位置名不副实。
- **累积式，本地越用越全**：断网可刷深度随时间增长，是真实的收益；但每次启动仍花 20 次请求、收益递减，而首页次序需要一个额外规则来维持稳定。
- **只拉第一页（18 部）**：几秒就跑完；但断网只能刷两三屏，滑到底就得等网络。

## Consequences

- 本地为空时首页走网络，所以**首次启动的体验与改动前完全一样**，不会退化。
- **断网只保证首页看得见。** 详情页要单独打一次接口拿分集列表，360 部全缓存不现实，所以断网时点进任何一部都会失败——那条路径给说清原因的错误态，不是转圈后报一句网络错。
- 某个标签拉失败**只保留该标签的旧数据**，其余标签照常替换：不整批回滚，也不给首页留半新半旧的缝。
- 「清除缓存」连快照一起清（与榜单缓存、封面的理由相同：可重建的本地副本）。**搜索历史不受影响**——它是用户数据，有自己的清空入口，跟收藏、观看历史一个道理。
- 上游抖动漏拉的那几部会从首页消失，直到下一次启动导入回来。这是整批覆盖的固有代价。
