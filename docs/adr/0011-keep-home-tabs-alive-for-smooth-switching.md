# 首页四个标签的封面常驻内存，用内存换切标签的流畅度

首页内部那四个标签（综合 / 真人剧 / 漫剧 / AI剧）原来每次切走都会把整页 dispose（`PageView` 的默认行为），切回来整棵树重建、封面重走「磁盘读 → 解码 → 220ms 淡入」——用户看到的就是「切标签时卡一下」。现在两件事一起做：

1. **四个标签页 keepAlive**（`_FeedViewState` 的 `AutomaticKeepAliveClientMixin`）：切回来不重建、封面不重解码、滚动位置也留住。底部三个页面本来就是这个口径（`home_shell.dart` 用 `StatefulShellRoute`/`IndexedStack` 正是为了保住滚动位置），首页内部这四个标签只是补上了同等待遇。
2. **启动后预热另外三个标签的首屏封面**（`_LibraryPageState._warmOtherTabs`）：keepAlive 只管**重复**切换，**第一次**进某个标签仍要第一次解码它的封面。这一条把那 4–6 张提前解码进内存 `ImageCache`——热过的封面连淡入都不放（`octo_image` 的 `wasSynchronouslyLoaded` 分支）。

**实测代价（Redmi K60，release）**：只开过综合 **169 MB** PSS；四个标签都走过一遍 **355 MB**，其中原生堆 +138 MB 就是解码后的封面。

**为什么它会超过 `ImageCache` 那 100 MB 上限**：上限只管**能被淘汰**的那部分。keepAlive 让四个标签的封面仍被 widget 引用，属于「活图」，既不计入上限、也挤不掉。所以实际占用是「100 MB 可淘汰 + 四个标签各自的活图」。这是刻意接受的，**不是泄漏**：`SliverGrid` 仍会回收滚出屏幕的卡，每个标签常驻的只是视口附近那一屏（约 8–12 张），不会因为往下滑就一路涨。

## Considered Options

- **不 keepAlive，改成「点标签时热那个标签的首屏」**：常驻内存最小。但首页的 `PageView` 在转场时就会开始构建目标页并请求同一批封面，`ImageCache` 按 key 合并同键的并发请求——所以预热与页面自己的加载会汇成同一条流，**总时长不变**，只是多写了一层代码。
- **只热数据（启动时把四个标签的 feed 都 ensureLoaded）**：实测一个标签 86 行、94 KB 的 payload 解析成 `Drama` 只要 **2–5 ms**（JIT 上界，真机 AOT 更快），读库那次也是异步的。数据这一段根本值不出「卡顿一下」，热它解决不了这件事。
- **把 `gridCoverWidth` 从 480 降到 400**：每张 1.64 → 1.14 MB，首访解码与显存上传降三成、常驻那 138 MB 也降三成。**这是唯一能减少总工作量而不是挪时间的办法**，没采用是因为 480 是按 xxhdpi 的 161dp（需要 483 px）算的，降到 400 会让海报在 3x 屏上被放大 1.2 倍。真要省内存时这是第一顺位。
- **给个「启动预热」开关**：与「不做设置开关」这条既有口径一致（榜单预热、剧库导入都没开关），不做。

## Consequences

- 预热只在**快照非空**时有活干。全新安装或清缓存后第一次启动，三个标签的快照是空的、`ensureLoaded` 要走网络，首屏仍然会有那一下——那时没有任何东西可预热。这是「本地优先」的固有代价。
- 预热**必须先 `ensureLoaded` 再热**：`LibraryFeed` 会把新拉到的那一页插到最前（`absorbDramas` 的 `atTop`），只按快照热的话，恰好在新剧上架时热的会是被挤下去的旧那几张。先加载 feed 的净请求代价约 0——`/reading/distribution/category/` 在 TTL 缓存白名单里，feed 拉的第一页会被缓存住，导入器随后拉同一页时直接命中。
- 预热**串行**跑、且跳过当前标签：串行让同时最多只有 3 张封面在飞，当前标签的首屏要抢同一批解码与显存上传，让它先赢。
- 内存这个数**没有在低端机上量过**。355 MB 是 8–12 GB 机器上的数；4 GB 机器上如果被系统杀，第一顺位是把 `gridCoverWidth` 降到 400。
