# App 接口失效时降级到网页源；空响应体不算成功

红果的 App 签名接口会以 **HTTP 200 + 空响应体**表示「这个入口不再供数」。App 详情
`/novel/player/video_detail/v1/` 现在就是这样（换 host、GET/POST、加 `book_id` 全是空体；
`/video_detail/` 返回 404，说明路径还在、只是不再吐数据）。当时 `fetchDetail` 只有 App
这一条腿，于是点开任何一部剧都报「红果 App 接口未返回有效数据」，而**所有测试都是绿的**
——契约测试只比对纯函数向量，控制流（有几条腿）不在比对范围内。

所以：**每条能力都保留 App → 网页两条腿，App 先试**；网页那条腿的数据是完整的
（`seriesDetail` 的标题、简介、标签、分类、集数、`vid_list` 都在，`vid_list` 长度与分类
接口给的集数逐部一致），所以它不是降级方案，是眼下唯一可用的源。顺序保持 App 优先，是为了
与 Go 包和参考实现（`果果剧库`，两边 `dramaFromAny` 与签名算法逐字相同）不分叉——上游哪天
把 App 详情放回来，自动就用回它。

分类这条腿多一条约束：**一个标签一旦降级，整个会话都走网页，不再回 App**。App 分类是
`offset + session_id` 坐标系，网页分类是页码坐标系，混着走会让游标失去意义，症状是翻页
重复或跳页。降级状态只记在分页器实例上、不落盘，所以下次启动会重新先试 App——上游恢复了
就自动回来。

空响应体与业务码非 0 的响应**不进 TTL 缓存**。原来只看 `statusCode == 200`，而重试只在非
200 上才有效，于是那份空体被钉住五分钟、这五分钟里每次重试都命中它、必然失败。症状是
「怎么点都是未返回有效数据」，重启才好，极难归因。

## Considered Options

- **详情直接只认网页**：省一个注定无用的请求，代码最短。但会与 Go 包分叉，且上游恢复 App
  详情后要手动改回来，还会丢「播放量」这个字段（只有 App 详情给）。
- **照搬参考实现收备选地址的方式**：它把 `main_url` / `backup_url` / `url_list` **全当同画质的
  并列档位**收进 variants，靠用户或播放器自己挑。那会让画质面板每个档位冒出重复项（同片源
  不同 CDN），而且拿不到「主地址挂了」这个信号。这里改成 `Media.backupUrls` 单独存、取流后
  依次探活，胜者写回 `url`。
- **分类只兜首屏 / 照搬参考的窄口径**：参考只在「App 返回 0 条 + 该标签尚未初始化」时兜，
  救不了「已经翻了几页、App 中途死掉」——而本次故障正是这个形状（接口是突然死的）。所以
  选了整标签降级。
- **只按状态码判成功入缓存**：见上，会让一次空体持续五分钟。

## Consequences

- 详情页的**播放量**要从分类快照用 `mergeDrama` 并回来——网页不给播放量，直接换会让那一行
  在详情到达的瞬间被抹掉。深链进来（没有分类快照）时补不了，认了。
- 「综合」标签**兜不了**：它走推荐接口，网页没有等价物。参考实现也只兜 `short_play`。
- 网页分类每页 24 条、`totalPages=34`，App 分类每页 18 条。降级后列表密度与剧库快照粒度
  会变，这是上游给的、无法对齐。
- 网页详情与评分是**同一个页面**（`seriesDetail` 与 `seriesSocialInfo` 同级），所以详情
  落到网页之后，评分那次请求基本都是一次 TTL 缓存命中。
- `series_id` 对不上时直接判失败：网页给了就核对，宁可报错也别把别的剧的分集挂上去
  （Go 那边不核对，这是 Dart 更硬的一处）。
