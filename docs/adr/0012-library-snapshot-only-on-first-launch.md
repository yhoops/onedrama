# 剧库只在首次进入 App 时自动拉一次，之后手动触发

[ADR-0008](0008-library-snapshot-on-every-launch.md) 的口径是「**每次启动**自动从红果拉四个一级标签各 5 页」。代价是每次启动固定 20 次签名请求加 350 多张封面下载（约 8.6 MB），跑十几秒——而这笔开销**绝大多数启动都白花**：上游的上架节奏是每天几十部，不是每次启动几十部。

真机上还撞到了更硬的一堵墙：一小时里连跑四轮导入之后，有一轮**四个标签全挂**（`逐标签 0:-1 1:-1 2:-1 3:-1`），几分钟后再启动又恢复正常。同一时刻用 Go 参考实现、换个设备号打同一个接口，549 ms 就拿到了数据——所以那一挂是**设备级的风控/限流**，不是上游故障，也不是代码坏了。

改成：**只在首次进入 App 时自动拉一次，之后由设置里的「更新剧库」手动触发。**

判据是一个 prefs 标记（`library_startup_import_done`），**先置位再跑，失败也算跑过**。这一点是刻意的：若按「快照为空就跑」判，那么用户按过「清除缓存」之后下一次启动又会被自动拉一份——而清缓存本来就是为了腾空间，把它填回去与用户意图相反；首次导入碰上下线也要手动点一次，这与「不打扰」是一致的。

## Considered Options

- **快照为空就自动跑**（全新安装、清缓存后、首次导入失败后都会跑）：最省心，且能自愈。没采用是因为它会与「清除缓存」直接打架，见上。
- **每次启动都跑**（ADR-0008 原样）：换来「冷启动秒开 + 断网可刷」始终新鲜。放弃它是因为那笔开销按天算完全没必要，而且反复启动会触发限流。
- **定时或后台刷新**：应用在后台做网络请求在 Android 上受限，而收益只是「用户不用点」；不值得为它引入 WorkManager 那一套。

## Consequences

- **剧库会变旧，直到用户点「更新剧库」。** 因此设置页那一行右侧的**时间戳不能省**——它是「这份数据多旧」的唯一指示器。这也是当初把「`267 部 · 3 分钟前`」而不是只写部数的理由（ADR-0010 里记了）。
- **清缓存之后不再自动拉**：本地没有快照时首页仍然可用（`LibraryFeed` 会走网络），但**断网时首页是空的**，要手动点一次「更新剧库」才恢复离线可看。这是刻意的取舍。
- **首次导入失败也要手动点**：标记先置位，所以失败之后不会自动重试。
- **首次启动那一次的封面预热无活可干**（快照还是空的），所以那一次的首次切换标签仍会卡一下；之后每次启动都有快照，预热照常。见 [ADR-0011](0011-keep-home-tabs-alive-for-smooth-switching.md)。
- 顺带减轻了「本次新增」被上游窗口旋转虚高的问题（见 `plan.md` 阶段 6 的已知问题）：导入变成用户主动、间隔拉长之后，那个数字里真实上新的占比会高一些——但**没有修掉**，漫剧那一支的旋转仍在。
